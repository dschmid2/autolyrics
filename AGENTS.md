# AGENTS.md — Technical Context & Guidelines for AI Agents

Welcome to the **Autolyrics** repository. This document provides technical context, architectural rules, and guidelines for AI agents working on or modifying this codebase.

---

## 1. System Architecture Overview

Autolyrics is a lightweight, real-time web application for synchronized song lyric projection and stage display.

* **Backend**: Node.js + Express (`server/index.js`) + WebSocket (`ws` library on `/ws`).
* **Frontend**: Single Page Application (SPA) in React 18 (`src/index.jsx` → `src/App.jsx`, split into `views/`, `components/`, `hooks/`, `lib/`), styled with Tailwind CSS (`src/styles.css`), icons from `lucide-react`, QR codes via `qrcode`.
* **Legacy Client**: `public/legacy.js` — a dependency-free ES5 client that re-implements the `/live`, `/stage` and `/player` displays for old browsers (e.g. old iPads / Safari).
* **Data Storage**: Separate JSON files (`data/songs.json`, `data/playback.json`, `data/players.json`, directory overridden via `DATA_DIR` environment variable, with automatic backwards compatibility for legacy `data/state.json`).
* **Media Uploads**: Audio files (MP3s) uploaded via `POST /api/upload` (multer, field `audio`, max 100 MB), stored in `data/uploads/` and served statically via `/uploads/`.
* **Build System**: `esbuild` for bundling React JSX to `public/bundle.js` and `tailwindcss` CLI for compiling `public/styles.css`.
* **Deployment**: Multi-stage `Dockerfile` (port `8080`, `DATA_DIR=/data` volume), `docker-compose.yml`, and GitHub Actions (`.github/workflows/`) that build and push a multi-arch (amd64/arm64) image to GHCR on pushes to `main`.

## 2. Key Codebase Directives & Rules for Agents

### Source vs. Artifacts
* **DO NOT EDIT ARTIFACTS**: Do not edit `public/bundle.js` or `public/styles.css` directly (both are git-ignored build outputs). Always make edits in `src/` (or `shared/`).
* `public/legacy.js`, `public/index.html` and `public/fonts/` are **source files** and are edited directly.
* **ALWAYS RUN BUILD**: Whenever you modify files in `src/` or dependencies, you **MUST** run:
  ```bash
  npm run build
  ```
  This command executes three sub-scripts:
  1. `npm run build:version` -> generates `src/version.json` and `public/version.json`
  2. `npm run build:css` -> minifies Tailwind CSS to `public/styles.css`
  3. `npm run build:js` -> bundles React code into `public/bundle.js`

### Keep Modern and Legacy Clients in Sync
* Display-related changes to `ProjectionView`, `StageView` or `UnassignedPlayerView` (new playback settings, layout changes, line semantics) usually need an equivalent change in `public/legacy.js`.
* `legacy.js` must stay strict ES5: no arrow functions, `let`/`const`, template literals, classes, spread, or modern DOM APIs without vendor fallbacks.
* `public/index.html` decides which client to load (capability checks + user agent). It can be forced with `?legacy=1` or `?modern=1`, and it falls back to `legacy.js` if the bundle throws during startup.

### Keep Defaults in Sync
* Playback/display defaults live **once** in `shared/playbackDefaults.js` (`PLAYBACK_DEFAULTS`) and are used by the server and the React client. `public/legacy.js` cannot import modules: its initial `state.playback` mirrors them. When adding a playback/display setting, update `shared/playbackDefaults.js` and `legacy.js`.
* Read display settings with `getSetting(playback, key)` — never write `playback.x !== undefined ? playback.x : 64` with a hard-coded default.
* Per-player stage setting limits live in `shared/stageSettings.js` (server validation + client UI). `legacy.js` keeps its own key list (`PLAYER_STAGE_SETTING_KEYS`).
* Change status/position only via `withAnchor()` / `usePlaybackControls()` so `anchorEpoch` is always set in server time.

### Code Organisation
* `App.jsx` only wires things together. Put new screens in `src/views/`, reusable UI in `src/components/`, React state logic in `src/hooks/` and pure logic in `src/lib/` (or `shared/` if the server needs it too).
* `shared/` modules must stay plain CommonJS without dependencies (the server `require`s them; esbuild bundles them for the client). The Docker runtime stage copies `shared/` next to `server/`.
* Views that need the playback position call `useElapsed()` themselves; do not lift it into `App` (it re-renders every 100 ms while playing).

### Versioning Mechanism
* Version format: `<major>.<minor>.<build>`.
  * `major.minor` is maintained in `package.json` (`"version"`; its patch part is ignored). Bump major for incompatible changes (data format, WebSocket protocol), minor for features.
  * `build` comes from the `APP_BUILD_NUMBER` env var. In CI it is `github.run_number`, passed into the Docker build as a build-arg (together with `GIT_SHA`). Without it, the version is `<major>.<minor>.0-dev`.
* `scripts/generate-version.js` writes `src/version.json` (bundled into the React app) and `public/version.json` (read by the server). Both are git-ignored — never commit them. Fields: `version`, `build`, `commit`, `builtAt`.
* The Docker build has no git (`.git` is in `.dockerignore`); never derive the version from git inside the container.
* `.github/workflows/docker-image.yml` computes the version and tags the image with it, `latest` and the full commit SHA (`docker/metadata-action`).
* The server exposes the version via `GET /api/version`, `/healthz` and `serverVersion` in the `state` WebSocket message. `VersionBadge` (operator header, `/player` registration screen) shows the bundled version and offers a reload when it differs from `serverVersion`; `legacy.js` shows `serverVersion`.

### Language
* UI text, server log messages and the README are in **German**. Keep new user-facing strings German. Code identifiers and this file are in English.

## 3. Data Models & Synchronization

### Persistent State (`data/songs.json`, `data/playback.json`, `data/players.json`)
Application data is separated into three distinct JSON files. Writes are debounced (150 ms) and all three files are rewritten together.

* `data/songs.json`: Array of song objects:
  ```json
  [
    {
      "id": "demo-1",
      "title": "...",
      "bpm": 84,
      "timeSigNum": 4,
      "timeSigDen": 4,
      "timingMode": "bar_beat",
      "audioUrl": "/uploads/1700000000000_song.mp3",
      "audioName": "song.mp3",
      "audioOffset": 0,
      "lines": [
        {
          "id": "l1",
          "en": "Original lyric line",
          "de": "German translation",
          "mode": "bar_beat",
          "bar": 1,
          "beat": 1,
          "duration": "",
          "stageOnly": false,
          "comment": ""
        }
      ]
    }
  ]
  ```
  Line fields:
  * `en` / `de`: original text and translation (the translation is only shown on `/live`).
  * `mode`: timing mode, falls back to the song's `timingMode` (default `bar_beat`). Per mode the relevant fields are:
    * `sec` → `timeSec` (absolute seconds)
    * `relative` → `relativeSec` (seconds after previous line)
    * `bar_beat` → `bar`, `beat` (absolute, 1-based)
    * `beat` → `beat` (absolute beat count, 1-based)
    * `relative_bar_beat` → `relativeBar`, `relativeBeat` (after previous line)
  * `duration`: optional seconds the line stays visible (empty string = until next line; last line defaults to 4 s).
  * `stageOnly`: line is shown only on `/stage`, not on `/live`.
  * `comment`: short cue shown next to the line on `/stage` (comment column).
  * Plaintext import syntax (`parsePlaintextSongLines`): one line per row, a leading `*` marks `stageOnly`, a leading `[cue]` becomes the `comment`.
* `data/playback.json`: Playback state and display settings (see `defaultPlayback()`):
  ```json
  {
    "songId": "demo-1",
    "status": "stopped",
    "anchorEpoch": 1700000000000,
    "anchorElapsed": 0,
    "updatedAt": 1700000000000,
    "fontSize": 64,
    "stageFontSize": 64,
    "translationPercent": 60,
    "translationSpacing": 24,
    "positionX": 50,
    "positionY": 50,
    "liveWidthPercent": 100,
    "liveTextAlign": "center",
    "showHeartbeat": true,
    "stagePastLines": 2,
    "stageFutureLines": 2,
    "stageLeadSeconds": 0,
    "stageCommentWidthPercent": 20,
    "stageLineSpacing": 24,
    "stagePositionY": 0,
    "stageShowTitle": false
  }
  ```
  * `status`: `"playing"` | `"paused"` | `"stopped"`.
  * Timing model: the server never ticks a clock. Clients compute the current position as `anchorElapsed + (serverNow() - anchorEpoch) / 1000` while `playing`, otherwise `anchorElapsed`. Any seek/start/pause just sets a new anchor.
  * `anchorEpoch` is in **server time**. Always create it with `serverNow()`, never `Date.now()` — device clocks differ, and a stage device whose clock runs behind the operator would otherwise show the previous line after a jump. `serverNow()` = `Date.now()` + an offset each client estimates from ping/pong round trips (`recordClockSample`, in both `src/lib/clock.js` and `public/legacy.js`).
  * `currentIndex()` treats a line as started 50 ms before its timestamp (`LINE_START_TOLERANCE`) to absorb remaining clock sync error.
* `data/players.json`: Registered player devices:
  ```json
  {
    "<player_uuid>": {
      "id": "<player_uuid>",
      "role": "live" | "stage" | null,
      "lastSeen": 1700000000000,
      "online": true,
      "name": "iPad links",
      "stageSettings": { "stageFontSize": 80, "stagePositionY": 10 }
    }
  }
  ```
  The player ID is generated per browser and stored in `localStorage`. Every connected browser registers as a player (also the operator and devices opening `/stage` directly).
  * `name` (optional): operator-chosen device name (max 40 chars), shown in the player management and on the `/player` registration screen.
  * `stageSettings` (optional): per-device overrides of `stageFontSize`, `stageCommentWidthPercent` and `stagePositionY`. Only overridden keys are present; missing keys fall back to the global value in `playback`. The server whitelists and clamps them (`sanitizeStageSettings` in `shared/stageSettings.js`). Applied to `StageView` on that device — both on `/player` with role `stage` and on `/stage` — via `applyStageSettings()` (`shared/stageSettings.js`, re-exported as `applyPlayerStageSettings`) / `getStagePlayback()` (legacy). Limits: `shared/stageSettings.js`; UI labels: `PLAYER_STAGE_SETTINGS` in `src/lib/playback.js`; legacy key list: `PLAYER_STAGE_SETTING_KEYS` — keep the legacy list in sync.
  * `registerPlayer` must preserve existing fields (role, stageSettings) of a known player.

*(Note: A fallback migration automatically reads legacy `data/state.json` if the individual files do not yet exist. With no data at all, the server seeds a single demo song.)*

### HTTP Routes (`server/index.js`)
* `GET /` and static files from `public/`
* `GET /live`, `/stage`, `/player` → `public/index.html` (client-side routing)
* `GET /uploads/*` → uploaded audio
* `POST /api/upload` → `{ url, filename, originalName }`
* `GET /healthz` → `{ ok: true, version }`
* `GET /api/version` → `{ version, build, commit, builtAt }`

### WebSocket Communication Protocol (`/ws`)
* **Server to Client**:
  * `{ type: 'state', songs, playback, players, serverIp, serverPort, serverNow, serverVersion }` (sent on initial connection)
  * `{ type: 'songs', songs }`
  * `{ type: 'playback', playback }`
  * `{ type: 'players', players }`
  * `{ type: 'ping' }` (application-level keepalive)
  * `{ type: 'pong', t0, serverNow }` (reply to a client ping; used for clock sync)
  * The `state` message also carries `serverNow` (rough initial clock offset).
* **Client to Server**:
  * `{ type: 'registerPlayer', playerId }` (sent on every connect)
  * `{ type: 'setPlayerRole', playerId, role }`
  * `{ type: 'setPlayerName', playerId, name }` (empty name removes it)
  * `{ type: 'setPlayerStageSettings', playerId, stageSettings }` (replaces the player's overrides; `{}` resets to global settings)
  * `{ type: 'deletePlayer', playerId }`
  * `{ type: 'setSongs', songs }` (replaces the full song list)
  * `{ type: 'setPlayback', playback }` (replaces the full playback object)
  * `{ type: 'ping', t0 }` (`t0` = client `Date.now()`; sent every 10 s and in a short burst after connecting) / `{ type: 'pong' }`
* **Broadcast rules**: `songs` and `playback` updates are broadcast to all clients **except the sender** (the sender updates optimistically); `players` updates go to everyone. The server overwrites `updatedAt` on `setPlayback`.
* **Keepalive**: The server sends WS pings plus a JSON `ping` every 15 s and terminates unresponsive sockets. Clients send a JSON `ping` every 10 s, force-reconnect if nothing was received for 35 s, and also reconnect on `visibilitychange`, `pageshow`, `focus` and `online` (important for iPads waking from sleep).
* **No authentication**: any client on the network can change songs and playback. The app is meant for trusted local networks.

## 4. Frontend Component Structure (`src/`)

See the repository layout in section 1 for where each piece lives:

1. `theme.js` — `THEME_PALETTES`, `ThemeContext`, `useTheme()`, `useThemeState()`: light/dark theme for the operator UI (persisted in `localStorage` as `autolyrics_theme`). `/live` and `/stage` always use the dark stage colors.
2. `hooks/useSyncedState.js` — WebSocket hook for bi-directional synchronization with `/ws` (returns `songs`, `playback`, `players`, `connected`, `playerId`, `sendSongs`, `sendPlayback`, `sendPlayerRole`, `sendPlayerName`, `sendPlayerStageSettings`, `sendDeletePlayer`, `serverIp`, `serverPort`, `serverVersion`).
3. `useElapsed(playback)` (hooks) / `computeElapsed(playback)` (lib/playback): current playback position in seconds from `anchorEpoch` and `anchorElapsed`.
4. `useLineIndex(lines, playback, leadSeconds)` and `useSongCompleted(lines, playback)`: active line and end-of-song detection.
5. `computeLinesWithTimes(song)`: converts song lines (timed in `sec`, `relative`, `bar_beat`, `beat`, or `relative_bar_beat`) into sorted absolute timestamps (`t`) plus computed `bar`/`beat`. `updateLineTimestamp()` does the reverse when a marker is dragged.
6. `parsePlaintextSongLines(text)`: plaintext lyric import.
7. `useAudioBuffer`, `WaveformCanvas` & `WaveformEditor`: Web Audio decoding and canvas waveform with bar/beat grid, drag-and-drop line markers (`single` vs `following` drag modes), positive/negative `audioOffset`, zoom, numbered markers, and a "send to screens" toggle that drives the live displays from the editor's playback.
8. Views in `views/` (selected in `App()` via `useViewRoute()` from the URL path; `/live`, `/stage`, `/player` are real routes, the operator sub-views are internal state at `/`):
   * `ControlView` (with `TopMenuBar`): song selection, playback control (`usePlaybackControls`), jump-to-line, mobile QR codes.
   * `PlayersView`: list of connected devices, role assignment, deletion and per-device stage settings (`PlayerStageSettings`).
   * `ProjectionView`: audience view (`/live`) showing original line and translation, heartbeat dot, auto blackout if disconnected > 30 s or song ends; skips `stageOnly` lines.
   * `StageView`: teleprompter (`/stage`) with past/future lines, comment column, stage lead seconds and an optional static title bar with the song title (`stageShowTitle`, half the stage font size). Uses `useStageLineState()`: `activeIdx` (line being sung, white) vs. `positionIdx` (line the view is centered on). Before the first line starts, line 0 is centered but grey; after a line's duration or the song end the view stays on the last started line (grey). `legacy.js` mirrors this with `startedIndex()`.
   * `UnassignedPlayerView`: shown on `/player` until the operator assigns a role (`live` or `stage`).
   * `EditorView` & `SongEditor`: manage songs, line timings, MP3 uploads; `ImportExport` handles JSON file download/upload and plaintext import.
   * `OptionsView`: font sizes, text position/width/alignment, translation spacing, stage view layout, heartbeat dot (sliders via `components/form/RangeSetting`).

## 5. Development & Testing Workflow

* **Install dependencies** (required before building):
  ```bash
  npm install
  ```
* **Building Assets**:
  ```bash
  npm run build
  ```
* **Running Local Server** (default port `8080`, override with `PORT`):
  ```bash
  npm start
  ```
* **Docker**:
  ```bash
  docker compose up --build
  ```

There is no automated test suite or linter. When making changes to logic or UI, verify that:
1. `npm run build` completes with zero errors.
2. The server starts cleanly without syntax errors in `server/index.js`.
3. For display changes, `/live` and `/stage` work in both the modern client and the legacy client (`?legacy=1`).
4. There is no test runner; for refactors compare screenshots/DOM of all views before and after (e.g. with Playwright, which is available).
